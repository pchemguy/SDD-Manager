Release tags must always identify release commits established on the repository's actual default branch. The release commit is either a commit made directly on that branch or the merge commit that integrates the designated primary development branch into it. A revision-branch commit is not an eligible release source merely because it is reachable through a later merge. The designated development branch need not be literally named `dev`; its primary development role must be established rather than inferred from a name.

Release documents may be prepared and committed inside the active campaign's revision directory. Move the applicable documents to their established final locations, when needed, as part of the release commit. This allowance does not move campaign plans, reports or other retained evidence out of their revision directory. Preserve applicable human curation, exact finalized notes and existing release recovery protections.

The [GitHub lifecycle](../../../../.agents/plugins/sdd-manager/skills/sdd-forge/references/github-releases.md) and [release checks](../../../../.agents/plugins/sdd-manager/skills/sdd-verify/references/release-checks.md) inherit that source-selection gap. The repository publisher validates an exact source, notes digest and tag agreement but does not establish default-branch release provenance. These observations define the revision targets; they do not alter or invalidate closed releases.
