## Accepted browser guidelines

1. **Establish the actual need and environment.** Derive browser requirements from the selected target, task and verification strategy. Separate the product's supported browsers from the agent's execution host and available interactive browser tool. Browser planning does not require installation during document-only work; pure engine/CLI tasks acquire no browser prerequisites.
2. **Use dedicated, environment-contained browsers.** Chromium is the default; Firefox is permitted when required by the project's test matrix. All other browsers, including Chrome, Edge and WebKit, are prohibited for agent use. Download missing binaries into the project or dedicated execution environment and use isolated profiles, caches and downloads. Reuse only compatible environment-owned installations. Do not search for/use pre-existing user/system browsers, personal profiles or running personal sessions, or modify global browser installations. Apply the same requirements to agent browser tools; unavailable provenance is not proof of compliance.
3. **Use normal project setup and compatible framework assets.** Inspect declared dependencies, lockfile, configuration and setup/test commands. Establish that environment when execution is needed; do not introduce Playwright or another framework by default. When Playwright is selected, use its project-installed package/CLI and compatible managed builds, explicitly install Chromium and required Firefox only, and configure the same environment-contained browser path for installation and execution. Standard Playwright supports its patched Firefox build; stock Firefox is unsuitable. Do not use bare all-browser installation, branded channel installation, global/ephemeral CLIs or machine browser discovery as shortcuts. Include concise CMD and POSIX setup examples without fixing incidental package versions.
4. **Preserve the required coverage.** Provision only the permitted engines, operating modes and capabilities required by the selected contracts. The allowlist does not require both engines for every task. Resolve any existing requirement for a prohibited browser through the owning decision/amendment workflow; do not run it or silently rewrite its acceptance. Keep Windows CMD and other host commands appropriate to the actual execution host.
5. **Verify through the real project path.** Use its actual runner/application integration and representative required capabilities. Retain the existing session/teardown, rendering/font/Canvas, native-event and reproducibility distinctions. A manual page visit or agent browser session does not establish that the project's automated browser environment works; a launch smoke does not prove full acceptance.
6. **Recover from an observed failure.** Capture the failing normal command and relevant cause, then diagnose download/source/version, cache/configuration, host dependencies or launch/runtime problems. Use bounded supported remedies within scope that preserve the browser allowlist and dedicated-environment boundary. A container or controlled remote environment must meet the same rules; an existing agent browser session is not a fallback exemption. Record the cause, setup difference and resulting evidence. Report an unresolved affected check as blocked; never substitute a system/disallowed browser or silently reduce coverage.
7. **Keep setup reproducible and evidence honest.** Retain the necessary project setup commands/configuration, version association and actual results in existing project documentation/checkpoints. Preserve unrelated caches/toolchains. Report missing required coverage as missing; do not relabel modeled events, an alternate browser or one successful launch as the original required evidence. No extra environment registry is needed.

These rules apply to agent browser execution; they do not require browser installation for unrelated work or select an automation framework for every project. Examples and assessment cases remain abstract and illustrative; they do not restrict product scope or require extra features. This accepted policy supersedes the opening proposal's exceptions for arbitrary existing branded/remote installations.

## Assessment cases

| Abstract situation | Expected route |
| --- | --- |
| Browser task lacks its declared automation environment | Prepare its declared framework and dedicated Chromium; add dedicated Firefox only for required coverage. |
| Correct browsers already exist inside the execution environment | Reuse compatible contained binaries and isolated state; verify the actual project path without mandatory redownload. |
| A personal/system browser or running session is available | Do not discover/reuse it; provision the permitted dedicated copy. |
| Existing contracts demand a prohibited browser | Retain the requirement/conflict, seek its authorized amendment and block that check; do not run the browser or silently replace the contract. |
| Declared setup fails | Diagnose and apply supported policy-compliant recovery; report remaining required evidence blocked. |
| An agent tool or remote endpoint offers a browser | Establish environment ownership, allowed engine and state isolation before use; availability alone is insufficient. |
| Existing project uses another supported automation framework | Follow its toolchain; the Playwright guidance is conditional. |
| Required matrix is only partly available | Retain the remaining coverage gap and original acceptance boundary. |
| Only an interactive agent browser is available | Distinguish its evidence from a working project automation harness. |
| Selected work is document-only or browser-independent logic | Do not provision browsers unnecessarily. |

## Technical basis and persistence

Official guidance checked on 2026-10-19: [Playwright browsers](https://playwright.dev/docs/browsers) associates package versions with specific browser builds, provides configurable Chromium/Firefox installation paths and requires patched Firefox. It warns that branded Chrome installation uses the normal OS location and ignores PLAYWRIGHT_BROWSERS_PATH. [CI setup](https://playwright.dev/docs/ci) establishes dependencies and browser assets before tests; [BrowserType launch](https://playwright.dev/docs/api/class-browsertype#browser-type-launch) cautions about custom executables. These support conditional Playwright details; the allowlist/isolation policy comes from the human. Do not pin an incidental current release in generic plugin policy.
