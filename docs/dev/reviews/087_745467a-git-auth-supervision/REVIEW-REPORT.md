## Observations

The screenshot shows an Antigravity process hierarchy reaching cmd.exe, Git, git-remote-https.exe, sh.exe, another Git process and git-credential-helper-selector.exe. The human reports that this operation effectively remains stuck indefinitely. The image establishes that the selector was launched as part of that Git process tree; it does not establish the top-level Git arguments, selector implementation/version, exact wait condition, token validity or a GitHub permission rejection. It cannot prove that the bundled recovery CLI was invoked. Raw workstation usernames/PIDs and the image itself are not copied into repository evidence.

The human subsequently confirmed “Yes” and “token is fine” after the proposed supervised path/direct-token recommendation. Treat the supplied token as valid for this investigation and retain it; no replacement or permission/ACL repair is indicated. The accepted routing decision is to bypass inherited selectors when an eligible supplied token is selected. This confirmation does not turn the screenshot into a new independent provider-authentication test.

Current [Git workflow monitoring](../../../../.agents/plugins/sdd-manager/skills/sdd-manage/references/git-workflows.md#monitor-pending-git-operations) requires bounded monitoring from the first attempt, but delegates observation, cancellation, diagnosis and uncertain-effect reconciliation to the agent. [Credential recovery](../../../../.agents/plugins/sdd-manager/skills/sdd-manage/references/credentials.md) first attempts existing shell authentication and selects the optional [recovery utility](../../../../.agents/plugins/sdd-manager/skills/sdd-manage/scripts/git-auth-recover.mjs) after a classified failure/blockage. Consequently the first helper invocation is outside the utility's runtime control. More instructions alone do not supply a deterministic deadline or cancellation implementation.

The recovery utility already resets inherited helpers for its token-assisted operation, supplies protected credentials only to the selected HTTPS context, preserves independent push/readback summaries and verifies the exact ref. Those useful protections remain relevant. Its [guide](../../../../.agents/plugins/sdd-manager/skills/sdd-manage/scripts/git-auth-recover.md) explicitly limits its timeout to individual children and excludes supervision of earlier tasks/hostile descendants. Source processResult uses spawnSync with a timeout and SIGKILL; recover performs multiple such operations without a shared overall budget. privateHelperContext also creates fresh default child bounds. This is an implementation limit to address before promoting the utility to the normal deterministic entry point, not evidence that its timeout caused the pictured Windows hang.

## Native offline probe

On Linux/Node.js 24.19.0, an isolated `git credential fill` invocation used an explicitly configured synthetic helper that signaled startup and then waited. No network or real credential was used. GIT_TERMINAL_PROMPT was zero, GCM_INTERACTIVE was never, askpass channels were empty and core.askPass was disabled. The helper started and Git remained running at the probe's two-second external deadline, with no credential stdout. The probe terminated its own isolated process group and reaped its direct child. This demonstrates that prompt-related flags do not enforce a deadline on an arbitrary helper; it does not reproduce the actual Windows selector or establish production cleanup behavior.

The [Node.js 22 child-process documentation](https://nodejs.org/download/release/v22.19.0/docs/api/child_process.html#child_processspawnsynccommand-args-options) distinguishes synchronous timeout signaling from completed process exit, and its kill/close sections distinguish parent termination, descendants and inherited streams. The [Git credential protocol](https://git-scm.com/docs/gitcredentials) documents external helper execution and resetting the helper list with an empty setting. Microsoft's [taskkill documentation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill) supplies a Windows-native PID/tree operation; it is a candidate backend to validate, not proof that every orphan/cleanup race is solved. Sources were checked on 2026-10-19.
