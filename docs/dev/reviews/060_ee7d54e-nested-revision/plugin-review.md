# Review plugin composition and coordination

## Scope and output

Review plugin-level capability boundaries, shared entry guidance, composite workflows, coordination and ownership. Assess the current supported package and report actionable findings. Inspect individual skills and references where a plugin claim or handoff depends on them; keep the review bounded by the requested scope.

A collection of independently used capabilities does not need the same entry or coordination structure as an integrated workflow system. Identify the accepted plugin design and assess its actual responsibilities. A review does not introduce a coordinator, common workflow entry or additional effects by implication.

Format conformance, content review and observed behavior provide different evidence. Use the owning format/structural tooling for metadata and package validity; this procedure assesses how capabilities form a usable system. Source review does not establish installation, host discovery or runtime invocation.

## Plugin composition and ownership

| Concern | Assess |
| --- | --- |
| Capability boundaries | Do skills have distinct responsibilities, useful outputs and understandable activation conditions? Are overlapping triggers resolved without requiring the user to know internal names? |
| Workflow decomposition | Do composite paths connect focused capabilities through meaningful handoffs? Are closely related internal branches kept together where independent capability boundaries add no value? |
| Shared ownership | Do common conventions, prerequisites and reporting rules have identifiable owners? Are summaries consistent with them, with justified short reminders rather than competing procedure copies? |
| Coupling and loading | Can the selected path load only the relevant skills/modules? Are dependencies explicit and available, without requiring the entire plugin context for every request? |
| Package and client boundary | Are advertised capabilities actually supplied and referenced files within the applicable package boundary? Are client extensions and unverified invocation behavior distinguished from portable structure? |
| Human and agent documentation | Do user-facing examples explain supported behavior while agent guidance supplies selection and execution boundaries? Are source-only development instructions kept out of runtime dependencies? |

For repeated guidance, identify its canonical owner and the decision protected by each summary. A shared entry or coordinator can highlight a consequential rule at a handoff; a full second procedure increases maintenance risk. Judge concision by sufficient explicit guidance for the intended models, not a byte/word quota or speculative token savings.

## Integrated plugin entry review

Apply this section when the plugin defines a shared workflow entry. A custom file such as PLUGIN.md needs an explicit purpose, loading path and availability fallback: it is not a standardized discovery or invocation guarantee. Essential operations must remain reachable through supported skill entries and their owners when that custom entry is unavailable.

| Entry concern | Review criterion |
| --- | --- |
| Orientation and coordinator pointer | Does the entry identify the plugin's capability system, relevant common prerequisites and any coordinator, with a clear condition for loading it? |
| Request-to-capability routing | Can an agent resolve ordinary requests to a supported owner or path from entry guidance, without opening all skill procedures or asking the user to name internals? |
| Composite summaries | Are purpose/trigger, principal owners, outputs, consequential handoffs and stops clear, without repeating every execution procedure? |
| Prominent obligations | Are shared authority, acceptance, persistence or other domain constraints visible before the actions they govern? Are detailed gates linked to their owners? |
| Projection and source fidelity | Do summaries agree with operational owners? Does any essential rule exist only in an optional custom entry? |
| Established context | Can follow-ups remain with an already active owner? Does unclear interpretation route to appropriate recovery rather than restart discovery or guess missing decisions? |

Keep workflow entry, established-context use and missing-context recovery distinct. A plugin entry can establish the owner needed for subsequent requests without interpreting every later task itself. A capability directory and a workflow summary serve different selection questions; neither should silently become a second full procedure catalog.

## Coordinator review

Apply this section when the plugin includes coordination. Assess the coordinator as part of the plugin's architecture and inspect its relevant entry/modules; do not presume a particular name, branch model, backend or mandatory approval sequence.

| Coordinator concern | Review criterion |
| --- | --- |
| Selection and continuity | Does it establish enough context to select a path, reuse an applicable workflow or recognize a material change? Are the decision and its basis communicated at consequential boundaries? |
| Shared readiness | Does it establish the prerequisites and human decisions needed by the next owner, keeping authority, readiness and performed state distinct? |
| Delegation | Are responsible skills and handoff inputs/effects/expected results clear? Does the coordinator preserve focused ownership instead of reimplementing each skill? |
| Boundaries across handoffs | Do scope, unresolved acceptance, requested stops and actual authorization survive transitions and recovery? Can a child operation finish without automatically resuming its parent? |
| Results and blockers | Does it collect actual evidence, reconcile blockers and return the correct completion boundary? Are unavailable capabilities and uncertain external effects reported rather than assumed complete? |
| Entry/module structure | Are general coordination decisions visible in the coordinator entry, with conditional detail under accessible owners? Does moving procedure out of the entry preserve required pre-action guidance? |

The shared plugin entry may project coordinator behavior; the coordinator may own canonical orchestration instructions. Do not impose the projection-only rule on that canonical owner. Inspect both sides of a consequential handoff and identify which layer selects, establishes readiness, executes, verifies and returns control. Ordinary context reuse and recovery must not depend on a custom plugin entry being loaded again.

## Review procedure

1. **Establish scope and source.** Pin the inspected package, intended capability model, requested outputs/effects and evidence limits. Identify actual installed/package contents and development exclusions where relevant.
2. **Map responsibilities.** Identify entry, coordinator, focused skills, shared guidance and optional tools/extensions. Trace ordinary request routing and selected composites; do not infer missing components from a preferred template.
3. **Assess composition and duplication.** Inspect section purposes, information order, loading conditions, repeated procedures and ownership against the criteria above. Distinguish necessary prominence from repeated detail.
4. **Trace affected transitions.** Check prerequisites, carried context, authority, human decisions, result evidence and stop on both sides. Include contextual follow-ups and recovery, not only fresh entry.
5. **Verify claims and cases.** Check actual links, containment, package inclusion and source agreement. If a behavioral trial is selected, supply only the intended initial context before observing discovery or routing; assess target agreement separately.
6. **Report and hand off.** Give located findings, consequences, confidence, bounded correction owners and objective rechecks. Preserve no-finding coverage and unresolved choices. Accepted revisions require affected entry/owner/projection rechecks under the project's actual persistence policy.

## Assessment contrasts and evidence

Use contrasts appropriate to the accepted design; do not make every trial compulsory. Keep domain-specific sample prompts and expected behavior in the plugin's own review material rather than importing its policies here.

| Contrast | Inspect or observe |
| --- | --- |
| Independent capability request versus composite workflow request | Direct owner use or appropriate coordination, without unnecessary full-system activation |
| Integrated entry available versus unavailable | Supported loading/fallback; no claim of automatic host discovery or dependence on an unavailable custom entry |
| Ordinary request versus request outside advertised scope | Clear owner/path or bounded clarification; no invented capability |
| Fresh workflow entry versus established owner/context | Needed discovery versus context reuse; no repeated selection ceremony |
| Recoverable context versus a consequential missing decision | Evidence-based recovery or targeted clarification; no guessed authority, acceptance or range |
| Assessment request versus authorized changes | Correct effects and return boundary |
| Shared prerequisite satisfied versus unresolved | Dependent work proceeds or remains blocked; delegation does not erase the gate |
| Child operation complete versus unfinished parent scope | Correct return and retained parent context; no implicit continuation |
| Narrow preparation result versus external publication | Requested outputs and permitted effects remain distinct |

For source review, record the actual instruction evidence and coverage. For a selected consumer trial, record source/model, initial context/request, loaded instructions, visible decisions, actual actions/output and reached boundary. Do not supply expected owners or reviewer answers to the consumer. A correct route does not prove downstream behavior, and structural validation does not prove universal client support. Report unrun or unavailable checks explicitly.
