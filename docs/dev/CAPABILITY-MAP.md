# SDD Manager capability map

This document records the plugin's intended capabilities, ownership, and present implementation status. It does not grant authorization to modify a project. **Included** means packaged as a skill. The central `sdd-manage` coordinator and the focused capabilities are included; packaging validation does not establish end-to-end client execution.

## Package rules

- Main documentation preparation uses [main preparation](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/main-preparation.md): enabled `sdd-docs-main` and nine issues verified before writes; four-file initialization with a partial-presence stop; task-only DOCS_TASKS and separate DOCS_PREPARATION control/approval evidence, with the selected mode's stop/reset or package-QC path. Complete preparation includes published docs integration, milestone closure and the final preimplementation checkpoint. Assets provide the AGENTS/task templates and root discovery protocol. Before writes, prospective AGENTS adoption supplies its target-project tracking default unless an established choice/controlling policy takes precedence; copying never resets that selection. Ordinary later edits retain first-approval completion; an authorized cursor reset reopens DOCS-002–009 and their existing issues while preserving documents and DOCS-001.
- Initialization executes/reuses [manual AI provenance setup](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/ai-logs.md) by default without an opt-in question; only an explicit human/project opt-out or deferral permits omission. Fresh setup has a preliminary DOCS-001 scaffold/default merge on reserved design-docs/ai-logs before design-docs/main; normal initialization closes DOCS-001 once. Enabled setup blockers require recovery/reporting, while transcripts and URL access are never required. Unmerged later manual records are not unfinished workflows. Detail stays in initialization and its assets, outside the coordinator/PLUGIN entry.
- Outside that main path, the first authorized SDD commit includes root disclosure/usage records and discoverable README links under [repository bootstrap](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/repository-bootstrap.md). sdd-manage coordinates adoption; sdd-implement/sdd-steer own their commits, sdd-report checks evidence, and sdd-orient inspects without writing. Existing repositories missing records receive a scoped next-commit backfill without history rewriting.
- A mutating workflow requires an eligible Git worktree. Read-only inspection and discussion may occur without Git. Creating a Git repository lies outside this plugin; DOCS-001 initializes SDD guidance in an existing repository.
- `sdd-manage` coordinates authorization, shared prerequisites, focused skills, work boundaries, and handoffs. Focused skills declare their prerequisites without implementing shared workflows.
- Publish and verify remote containment after **every workflow-owned commit** before further work or another commit, under [per-commit publication](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/git-workflows.md#publish-each-commit). Git commits provide durable implementation checkpoints. `sdd-orient` compares the last completed task commit with the owning checklist and pending changes, then hands the identified task state to `sdd-implement`. After retained-commit publication preflight, `sdd-implement` pushes eligible unpushed commits on the current branch to its established remote branch, even when the worktree is clean. Dirty state alone does not require reset.
- [Continuity](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/continuity.md) uses tracked HANDOFF checkpoints, automatic milestone/phase review-task and revision-finalization refresh, and recovery from subsequent owning records/Git. AGENTS routes startup; the coordinator requests an unselected continuation branch and restores nested parent context without automatic resumption. Ordinary task commits require no handoff edits; assets supply the HANDOFF template.
- Workflow branches follow the shared identity convention: revision/steering and feature names match retained campaign directories; main phase numbers come from accepted PLAN/TASKS. The coordinator branch manager owns local setup and transition without a hosting backend.
- Main task subsets push/pause on an incomplete phase branch; complete phases explicitly merge into the established main integration branch, and authorized next phases start from its verified published checkpoint.
- Scoped working branches retain task/amendment checkpoints. `sdd-manage` coordinates default explicit two-parent merges at verified boundaries, merged-state checks, and target publication. Steering targets the paused implementation branch and stops after integration. Incoming baseline synchronization preserves the receiving workflow and its unfinished boundary; completion returns to its recorded parent. Git merge and feature-document incorporation remain separate.
- Review/revision campaigns use stable ordered baseline directories `docs/dev/reviews/<campaign>-<slug>/` and matching `revision/<campaign>-<slug>` branches. `sdd-manage` coordinates review plans, review reports, accepted revision plans, and revision reports; focused review may use prompt-defined criteria. Relevant accepted decisions enter governing documents while campaign artifacts remain retained. [Revision modes](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/revision-modes.md) define nested parent suspension/return and explicitly authorized eligible reopening. Frozen unrelated campaigns remain unchanged; a reopened campaign retains its original identity/opening and cumulative integration summary.
- HTTPS Git publication uses the [supervised entry](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/credentials.md#deterministic-git-publication) from the first attempt, selecting eligible supplied-token authentication before inherited helpers and bounding process cleanup and exact-ref readback. sdd-conventions defines ignored repository `*.tkn` storage; sdd-manage selects/saves tokens and diagnoses access failures. Provider-specific permission profiles belong to the active backend, and Git transport access does not prove API access.
- Scripts are optional for deterministic, well-defined operations. External integrations are optional capabilities with explicit inputs, effects, and reconciliation rules.

## Bundled skill references

Distribute SDD Manager's skills together. Use ordinary relative Markdown links between bundled skills, and name the destination skill when requesting a workflow handoff. From `skills/sdd-design/SKILL.md`, for example:

```markdown
Before modifying the repository, use **sdd-orient**:
[repository orientation](../sdd-orient/SKILL.md).

Apply the shared
[Markdown conventions](../sdd-conventions/references/markdown-style.md).
```

| Reference | Purpose |
| --- | --- |
| Another skill's `SKILL.md` | Identify the capability and its entry instructions. |
| Another skill's reference file | Load shared guidance without selecting its whole workflow. |
| Named skill in prose | Describe routing or delegation; execution depends on the client. |

[Agent Skills](https://agentskills.io/specification#file-references) documents relative file references and progressive disclosure without specifying interskill dependency resolution or explicitly prohibiting sibling-relative `../` links. [Agent Plugins §4.1](https://agent-plugins.org/specification#41-general-requirements) establishes the resolved plugin root as the package-file containment boundary; §7.1 leaves client skill exposure unspecified. Neither defines a standard interskill dependency field or invocation syntax.

Validate resolved links against the plugin root, including filesystem link resolution. A sibling-relative target inside that boundary satisfies package containment; it does not establish universal client loading or routing support. The creator validator's individual-skill `resource-escape` findings apply a stricter standalone boundary and do not, by themselves, demonstrate a bundled-plugin containment defect. Independently distributed skills and installed-client behavior require their own checks.

## Core development workflows

The [canonical model](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/workflows.md#core-development-workflows) defines three purposes: main development builds the complete intended system; revision corrects, simplifies, or improves defined/implemented work, typically through review/revision records; feature adds a scoped capability through the necessary feature package before implementation. Stages can be entered when their inputs are established, and operations can be requested independently.

Completed incorporated feature sources are retained under `docs/dev/features/<campaign>-<slug>/` with repaired navigation and historical task status; active root sources remain until incorporation/ownership/archive gates are met.

Steering is the lightweight human-directed revision variant at a paused implementation checkpoint. It directly amends existing documents and implemented behavior without feature overlays or a mandatory formal campaign, integrates into the paused branch, and returns control without resuming the task list. Shared verification/persistence/integration rules remain applicable; taxonomy alone grants no extra scope.

## Workflow loading and reporting

`sdd-manage` owns [read-only workflow loading](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/workflows.md#workflow-loading): explain selected sources actually read, stages/checkpoints, authorized scope and next step in chat without project preparation or mutation. Its [scope/reporting protocol](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/coordination.md#scope-checks-and-reporting-detail) checks current authority before work and both path/change before writes. Event-based briefs and requested reporting detail preserve consequential decisions, evidence and human checkpoints; clarification does not accept an artifact. The [reporting profiles](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/coordination.md#reporting-profiles) provide Minimal, Standard (default) and Explicit shortcuts, retained in available workflow context/handoffs with scoped response overrides. At [composite bootstrap/recovery](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/coordination.md#composite-workflow-bootstrap-reporting), the coordinator announces temporary Explicit reporting, explains profiles briefly and declares Standard or the established human preference before dependent work. PLUGIN.md projects these instructions, while direct coordinator entry remains sufficient.

The user may explicitly [preapprove future human checkpoints](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/human-document-review.md#future-checkpoint-preapproval) at any point; retain scope/conditions without waiving technical, tracking or publication gates or expanding execution ranges.

Main preparation supports [doc-design modes](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/doc-design-modes.md): interactive/onepass by default, autodoc/onepass, autodoc with human-controlled multipass and autodoc/autoloop for predefined scope sequences. The mode owner defines approval/delegation, retained-document resets and DOCS-008 stops; the coordinator selects or recovers that context before document handoff. A completed autodoc pass does not select package QC or implementation.

ARCHITECTURE describes major structure and rationale; DECOMPOSITION refines logical responsibility and collaboration; SPEC defines observable guarantees linked to relevant structural owners/consumers. Conflicts return to their owners for accepted decisions. PLAN stages the complete intent through an early meaningful usable slice and small testable growth, with appropriate functional/usability decisions kept human-controlled.

The main design, SPEC, PLAN, and layout documents describe the intended system, strategy, and physical ownership. Temporary feature documents describe explicit deltas that are reconciled into the main documents when accepted. TASKS records the complete intended work breakdown and evidence-backed progress. An active FEATURE-TASKS records only the feature's executable delta; task IDs are unique across both lists, and reconciliation preserves verified status and Git evidence. Parent documents may link to focused children without duplicating their detailed requirements.

## Execution boundaries

- **Testing and verification:** `sdd-tdd` owns test strategy, design, and changes, including test execution during the development cycle. `sdd-verify` assesses whether the checks sufficiently cover the requested acceptance and exit conditions and runs the required verification campaign, including separate read-only implementation code review for milestone/phase review tasks. Both may execute tests for their respective purposes.
- **Verification evidence:** `sdd-verify` reports commands, environment, observed outcomes, acceptance coverage, blocked or omitted checks, and remaining uncertainty. Distinguish defects in the change, pre-existing failures, and environment problems when evidence permits. Passing checks do not establish untested acceptance conditions. Verification leaves task status unchanged and returns repairs to the active implementation workflow: `sdd-implement` for main task work or `sdd-steer` for a checkpoint amendment.
- **Documentation:** `sdd-docs` maintains docstrings, usage guides, and standalone explanations. Follow project conventions, with Google-style docstrings where applicable when no project convention overrides them. When authoritative design, SPEC, PLAN, layout, or task requirements need amendment, `sdd-docs` reports the location, issue, impact, and proposed amendment to the user and defers the decision. It does not edit those requirements or automatically invoke their owning skills; independent documentation work may continue.
- **Human-directed steering:** The human defines the amendment objective at a checkpoint and commands `sdd-steer` implementation. Steering assesses affected behavior and dependencies, directly amends the existing SPEC, PLAN, TASKS or active FEATURE-TASKS, design, and layout where needed, and aligns code, tests, and documentation. It creates no feature-document layer and requires no `sdd-integrate-feature` step. Use `sdd-tdd`, `sdd-docs`, and `sdd-verify` within that focused scope. For a reduction, verify that removed functionality is consistently removed and retained functionality remains valid; reassess affected completion claims while preserving stable task IDs and unaffected work.
- **Steering stop boundary:** `sdd-steer` verifies, commits/pushes the amendment, explicitly merges into the paused implementation branch, verifies/publishes the target, and reports, then stops. A blocked amendment resumes only on a human command. It neither hands off to nor resumes `sdd-implement`. The human separately decides when to resume the remaining task list.
- **Completion and reporting:** `sdd-implement` owns execution, repairs, completion checkboxes, commits, pushes, and issue-closure coordination for the main task-list workflow. `sdd-steer` owns corresponding operations within its human-commanded amendment scope. `sdd-report` presents the resulting evidence. Honor project-designated evidence locations; otherwise durable verification and authorized test-first exception facts accompany the owning entry or its existing linked evidence, or ordinary taskless reports/commit bodies; a separate verification journal is not required, and a verification map or scripts remain optional.

## Development-document preparation QC

sdd-conventions owns [shared QC invariants](../../.agents/plugins/sdd-manager/skills/sdd-conventions/references/development-document-qc.md); sdd-manage enforces [dependent-stage gates](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/document-qc-gates.md). sdd-specify reviews SPEC/design, sdd-plan reviews PLAN/SPEC plus relevant layout, and sdd-tasks reviews TASKS/PLAN separately from progress. sdd-report composes adjacent reports; the reviewing owner determines readiness from actual state and evidence. Authoring includes correction/recheck; review-only does not silently correct governing inputs.

SPEC gates PLAN, PLAN gates TASKS, and TASKS gates execution/hosted projection. Direct invocations use the same gates and implementation retains push-first. Meaningful scope and conformance are checked alongside delivery counts; dedicated review units remain mandatory but excluded from shape diagnostics. Material amendments invalidate affected assessments; unchanged concerns can retain supported evidence. Adjacent preparation reports and their appended correction cycles are distinct from implementation phase/milestone reports and campaign records. Scoped incorporation/steering preserve ownership and report unselected downstream invalidation; eligible archived feature QC reports remain beside their sources.

## Preparation, tracking and task persistence gates

[Human document review](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/human-document-review.md) is distinct from technical QC: necessary newly authored PROJECT, ARCHITECTURE, DECOMPOSITION, SPEC, PLAN, layout and TASKS roots, including needed feature counterparts, each have a checkpoint. Require human acceptance where the selected mode or explicit scoped preapproval does not cover it. Existing acceptable startup inputs need no retrospective interactive review; explicitly requested review or pending acceptance remains binding. Accepted preparation and adjacent QC reports follow the [preparation integration gate](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/branch-management.md#preparation-integration-gate) into the actual default branch, with merged checks and publication before a dependent implementation branch is created.

The manager owns the [tracking decision](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/tracking-decision.md) and [eligible-phase activation](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/phase-activation.md); forge owns hosted writes and association readback. Requested tracking remains pending until the eligible phase and its selected executable tasks have verified provider associations. Missing, partial or unknown initial/added-task projection blocks dependent edits/tests; an explicit decline takes the untracked route. An outage after verified activation may leave independent local completion and hosted closure pending, but cannot authorize unresolved dependent reviews or next-phase progression. Omission recovery preserves existing work and publishes verified retained commits without replaying implementation.

For TASKS/FEATURE-TASKS implementation, the [task commit contract](../../.agents/plugins/sdd-manager/skills/sdd-implement/references/completion-and-checkpoints.md#task-commit-contract) requires one task’s complete closing result, current evidence and initial completion transition together, with a leading single owning `[T-XXX]` and imperative summary. Aggregate task closure and a separate initial checkbox-only commit violate that contract. Explicitly authorized partial checkpoints leave the task unchecked; the closing commit includes remaining result/evidence/status and identifies prior checkpoints without repeating unchanged code. Continuation and pre-integration audits inspect actual commits and selected merge parents; invalid persistence needs scoped recovery, never an automatic history rewrite. DOCS_TASKS uses the coordinator's [main preparation](../../.agents/plugins/sdd-manager/skills/sdd-manage/references/main-preparation.md) persistence for initialization, first approvals and package QC, without the implementation audit. Taskless campaign actions and integration merges do not invent task IDs.

## Release ownership and evidence

[Complete release-message preparation](../../.agents/plugins/sdd-manager/skills/sdd-forge/references/release-message.md) handles prepare/draft/assemble/update requests for release messages/notes: manage coordinates context/ownership, forge collects validated changes, and report assembles applicable overview, compatibility/upgrade, highlights/other changes, installation, limitations and references. Retain root `RELEASE-NOTES.md` by default after preparation/publication, refresh/replace it atomically on repetition, and honor explicit path/template or editing-only scope. Highlights-only preparation remains a distinct narrower operation. A release request verifies current local notes coverage and stated version, refreshes stale material, and coordinates a release commit on the actual default branch, directly or as the merge from the designated primary development branch. That commit carries the same complete Markdown body used for GitHub; the release tag points to its verified published SHA. Matching version alone does not prove freshness. Final publisher handoff uses exact complete Markdown bytes, source association and hash; the internal highlights checkpoint alone is eligible for verified-consumption cleanup.

[Git highlights](../../.agents/plugins/sdd-manager/skills/sdd-forge/references/release-highlights.md) works independently of hosting: pin the complete release range, use adequate cumulative integration summaries and retain editorial decisions and coverage watermarks. Report owns complete-message assembly and curated body-only [release notes](../../.agents/plugins/sdd-manager/skills/sdd-report/references/releases.md). Package/workflow/release owners establish exact source, expected assets, notes transfer, one publisher, draft completeness, serialization and safe reconciliation. Verify owns [release checks](../../.agents/plugins/sdd-manager/skills/sdd-verify/references/release-checks.md); manage owns Git persistence and the advisory prerelease-review reminder. No task tracking is required for a standalone release.

The source repository’s [actual handoff guide](../../.github/RELEASE-HANDOFF.md) describes its single manual-dispatch publisher. It is repository tooling, not a universal packaged command. Keep local build, actual CI, hosted metadata, downloaded bytes and installed-client evidence distinct. A prepared ZIP or accepted dispatch does not establish release completion.

## Task audit recovery

The implementation owner's [task recovery](../../.agents/plugins/sdd-manager/skills/sdd-implement/references/completion-and-checkpoints.md#resolve-a-task-recovery) separates historical composition, current acceptance/evidence and ownership/authority. The manager reuses actual grants for forward repair/publication and the unchanged active range; missing authority, human pauses and specific historical-composition exceptions retain human decisions. Current acceptance needs exact source/condition evidence and affected task/parent/hosted reassessment, not aggregate green counts. [Publication preflight](../../.agents/plugins/sdd-manager/skills/sdd-implement/references/startup-and-continuation.md#push-before-task-work) and the Git owner's narrow corrective-persistence exception prevent blind pushing of known-invalid retained completions without changing normal per-commit cadence.
