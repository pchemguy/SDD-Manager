# SDD Manager source guidance assessment

## Scope and loading

Load this source-only companion when selecting or assessing instruction/handoff cases for PLUGIN.md, sdd-manage or an affected focused workflow. The [plugin development contract](PLUGIN-CONTRACT.md) owns normative responsibilities, gates, organization and package boundaries; ordinary entry/module edits load that contract first and select only relevant assessment coverage here. These cases assess existing requirements and do not add target-project requirements or authorize trials, repairs or external effects.

Keep source inspection, controlled execution, independent consumer trials and installed-client evidence distinct. The protocol and complete case library below support those selected assessments; case descriptions and examples are illustrative, not limits on supported domains or a mandatory scenario catalogue.

## Guidance assessment cases

The [Tetris](../demo/tetris/README.md) and [Calculator](../demo/calculator/README.md) guides provide project situations; canonical owners in the [contract](PLUGIN-CONTRACT.md) define expected behavior. Preserve C/K case identities. These are reviewer cases, not fixed commands or new project requirements.

Use an eligible Git repository, available required skills and working publication access for selected mutation trials unless a case states otherwise. Record actual tracking choice and requested range. Entry cases begin through PLUGIN.md; contextual cases begin with the active owner; recovery cases remove only the stated context. Assess owner/context discovery separately from downstream execution. A coordinator trial starts through sdd-manage without PLUGIN.md.

For source assessment, inspect the applicable instruction and handoff evidence. A selected consumer trial receives ordinary project facts and permitted instructions, not expectations or a named expected workflow. Retain source/model, actual initial context/prompt, selected owner, loaded instructions, visible decision, reached boundary and pass/gap/blocked/unrun result. Static checks do not establish live behavior or host discovery; routine continuation does not require a new selection brief.

Check that the selected module becomes available before its dependent action. Use the [plugin cases](#guidance-assessment-cases) and coordinator examples for project situations; add the relevant coordinator context. ## Workflow loading and reporting checks

Assess read-only workflow loading separately from project-document preparation: actual sources, relevant stages/checkpoints, scope and next step must be discoverable through either entry without implied writes or development authority. Selected instructions precede definitive procedure reporting and dependent work. Greenfield remains main development's starting context.

Compare default and human-requested reduced reporting on unchanged continuation, a material switch, an unavailable source and a pending approval. Check that repeated context can be omitted while consequential decisions, blockers, verification and human checkpoints remain visible. Clarification supplies requirements, not artifact acceptance. Check scope before work and both path and change before writes; reporting brevity cannot remove those obligations. These source contrasts add to the retained C/K cases without claiming model behavior.

Assess Minimal, Standard (default) and Explicit reporting through the canonical coordination owner. Check profile selection/switching, context/handoff continuity, one-response overrides and explicit source requests; compare a pending human decision under every profile. Profiles must preserve the same operational obligations and event-based reporting triggers, with no inferred model-strength selection or profile-state file. Entry summaries expose the shortcuts without becoming their canonical definition.

At composite-workflow bootstrap, material switching or context reconstruction, assess proactive announcement of temporary Explicit reporting, brief profile discovery and declaration of the subsequent Standard/default or established selected level before dependent work. Compare a known preference with lost context, and blocked recovery with an eligible handoff. Routine task continuation or minor evidence refresh must not replay this introduction. Respect scoped human overrides and preserve approval/range uncertainty.

## Task recovery assessment

Compare a premature verification claim with a malformed/split/bundled closing commit and with both violations together. Require separate classification, original failure/current corrected-condition evidence and truthful historical/current claims. The manager may reuse existing authority for a bounded forward repair, publication and unchanged active range; it cannot waive a historical composition violation or invent a lost grant. Compare verified retained commits with known-invalid/unowned completions: publication preflight holds unsafe results, permits only necessary authorized recovery/corrective persistence and restores normal publication before further work. Check direct implementation and coordinator/PLUGIN projections together without moving detailed recovery into either entry.
