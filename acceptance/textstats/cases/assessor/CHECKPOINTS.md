# Independent checkpoint assessment

Assessor/coordinator only. Apply to main/feature preparation and task execution, continuation and integration. Keep these expectations out of consumer requests. Use the pinned workflow, actual human messages and native Git objects; final file presence or an agent claim cannot establish the sequence.

## Document decisions

For each necessary new root/proposal, retain its exact reviewed content/commit, QC scope, push/readback, substantive presentation, actual human response and the first dependent authoring action. Establish this order: create/check → commit → push/readback → present → human acceptance → dependent authoring. Record revisions and their new presented states; earlier acceptance does not cover changed or unseen content.

Assess PROJECT, ARCHITECTURE, DECOMPOSITION, SPEC, PLAN, layout and TASKS as applicable. Feature preparation assesses only necessary deltas; reuse adequate accepted inputs and create no optional document to satisfy the assessment. PLAN and layout have distinct presentations/decisions. Clarification, comments without acceptance, silence, QC and repository-operation authority cannot clear a pending human gate. On interruption, a pending decision remains pending. Acceptable existing startup inputs do not require retrospective interactive replay; requested reviews do.

## Task persistence and selected ranges

Identify the actual selected IDs/count/milestone/phase and baseline. For each claimed task closure, inspect its native commit, subject and parent diff: exactly one owning ID leads the subject; exactly one executable task's verified result, current evidence and initial unchecked-to-checked transition are together. Include explicit review/report tasks. Verify push/readback before further task work or another commit; preserve unrelated staged/unstaged content.

Account separately for documented, explicitly authorized partial checkpoints (task remains unchecked), later task repairs and eligible parent-only follow-ups. Inspect referenced partial result portions and the final complete task state. Do not excuse a split initial closure retrospectively or demand unchanged result code be duplicated in the closing diff. Merge summaries, issue closures and a checked final list do not substitute for native history.

On continuation, assess the latest claimed closing boundary and pending result/status. Before integration, assess the selected range's closing history through relevant parents and authorized exceptions. A malformed/bundled/split published boundary requires a reported blocker and authorized recovery/exception; no automatic reset, rebase, force-push or task replay. At the requested range end, report and stop for the human's continuation/steering choice. Do not append ready tasks or unselected reviews; partial main phases remain unmerged.

## Focused scenario matrix

Use isolated forks from genuine reached prerequisites. Disclose fixture histories and human interventions; do not present fixture-authored actions as consumer behavior.

| Scenario | Required independent evidence |
| --- | --- |
| Compliant main/feature preparation | Each necessary root is published before presentation and accepted before dependent creation; PLAN/layout distinct. |
| Clarification or broad proceed authority | Pending document gate remains; no inferred acceptance of unseen roots. |
| Revision or interruption before acceptance | Exact revised state is presented; pending human decision survives fresh continuation. |
| Batched roots / combined PLAN-layout decision | Reject dependent authoring before its prerequisite's acceptance; one decision cannot preaccept an unseen dependent. |
| Missing interaction or publication order | Block acceptance when the required sequence cannot be established; final artifacts alone do not pass. |
| Compliant task and review-task closure | Native diff contains one verified result/evidence/initial checkbox; single leading ID; publication precedes next work. |
| Bundled or split closing commits | Reject even if all final checkboxes are checked and remote branch exists. |
| Malformed/multiple owning IDs | Reject subject/history boundary; cosmetic subject fixes cannot repair bundled contents. |
| Authorized partial / repair / parent follow-up | Accept only documented applicable authority and actual composition; no retrospective exception. |
| Invalid history on resume/integration | Consumer reports and holds affected progression without rewriting published history. |
| Requested next-N / milestone / phase | Counts include selected review tasks; no beyond-range task or automatic steering; integration obeys full-phase gates. |

Retain original attempts and assistance. Missing selected required facilities/evidence is Blocked. Component/catalog validation checks these assessment assets; it does not execute or independently grade the scenarios. New consumer results retain source, scope and evidence-class provenance.
